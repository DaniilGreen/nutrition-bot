# CLAUDE.md — как работать в этом репозитории

burnfat — личный Telegram-бот учёта питания (2 пользователя). Главный приоритет —
**точность учёта КБЖУ**; интерфейс вторичен.

## 0. Главный принцип: спека — источник правды

- **`docs/SPEC.md` — единственный источник правды.** Любая задача начинается со сверки с ним.
- **Меняется поведение → сперва правь спеку, потом код.** Не наоборот.
- **Фиксируй в спеке всё:** требования, решения, scope, договорённости, новые открытые
  вопросы. Не держи в голове и не прячь только в коммит.
- **Отталкивайся только от спеки.** Не реализуй того, чего в ней нет, не дописав сперва туда.
  Поведение без записи в спеку = недоделка.
- Ссылайся на требования по ID: `FR-*` (функции), `NFR-*` (нефункц.), `INV-*` (инварианты),
  `AC-*` (критерии приёмки), `D-*` (принятые решения). Новый кейс/баг → заводи AC и чини до зелёного.

## 1. Архитектура (clean)

```
bot (aiogram) / web (FastAPI)  →  application (use-cases + Protocol-порты)  →  domain (чистый)
                                         ▲
                infrastructure: db (SQLAlchemy) · nlu (OpenAI/Fake) · stt (Whisper) — реализуют порты
```

- **Модель C «LLM наполняет, БД фиксирует»:** LLM извлекает сущности и оценивает плотность
  (КБЖУ/100 г); финал считает `domain/nutrition.py`; БД фиксирует плотность навсегда. SPEC §6.
- Сервисы не знают про SQLAlchemy/OpenAI. Тесты — на in-memory фейках (`tests/fakes.py`),
  без БД и без вызовов LLM.

## 2. Инварианты — НЕ ломать (SPEC §6)

- Финальные КБЖУ считает приложение, не LLM (`INV-1`).
- Плотность пиннится при первом появлении продукта → детерминизм (`INV-2`).
- `meal_items` хранят снапшот КБЖУ — история не плывёт при правке каталога (`INV-3`).
- `canonical_key` — идентичность продукта; мусорные ключи (unknown/none/food…) → slug (`INV-4`).
- Граммовка — приоритетная цепочка `resolve_grams` (`INV-7`): явный вес → штуки×вес →
  курируемый размер блюда → оценка LLM → дефолт.

## 3. Рабочий цикл

- Запуск: `make up` (db + bot + api, миграции применяются авто). Логи: `make logs`.
- **`./app` смонтирован в контейнер** → правки кода видны сразу, но процесс бота должен
  перечитать модули: **`docker compose restart bot`**.
- Тесты: `make test` (в контейнере). **ВАЖНО:** `./tests` НЕ смонтирован — для свежих тестов
  монтируй вручную:
  `docker compose run --rm --no-deps -v "$PWD/tests:/app/tests" api pytest -q`
- Проверить, что вернёт LLM на ввод (дегустация NLU): одноразовый probe-скрипт под `app/`,
  гонять `docker compose run --rm --no-deps api python -m app._probe`, **после — удалить**.
- Нетривиальная логика (ветка/цикл/парсер/деньги/безопасность) → оставляй один runnable-чек
  (assert-`demo()` или маленький `test_*.py`). Ponytail: без фреймворков и фикстур.

## 4. Деплой правки поведения

1. Спека (если меняется поведение) → 2. код → 3. тест/probe зелёный →
4. `docker compose restart bot` → 5. коммит. README/SPEC держать в соответствии.

## 5. Коммиты (этот репо)

- Формат: `type(scope): subject` (imperative, без точки). Для крупного изменения — пустая
  строка и `#comment` на русском (что → почему → эффект, 18–30 слов). Мелкой правке — только subject.
- `type` по приоритету изменённых файлов: `infra`/`ci` > `fix`/`feat` > `refactor`/`chore` > `docs`/`test`.
- **Jira-ключа нет** — это личный проект (переопределяет глобальный формат).
- **НЕ упоминать Claude / Co-Authored-By** в сообщении.
- **Перед коммитом — гард `.env`:** `git ls-files --error-unmatch .env` должно падать
  («не отслеживается»). В `.env` реальные `BOT_TOKEN` и `OPENAI_API_KEY` — gitignored,
  НИКОГДА не коммитить и не пушить.

## 6. Ponytail (стиль кода)

Лениво = эффективно, не небрежно. Stdlib и нативное — первым делом; не плодить абстракции
ради «на будущее»; кратчайший рабочий диск. Сознательные упрощения помечать `# ponytail:`
с указанием потолка и пути апгрейда. Не упрощать: валидацию на границах доверия, обработку
ошибок (потеря данных), безопасность, явно запрошенное.

## 7. Что сознательно НЕ делаем (SPEC §4)

Фото/штрихкоды, микронутриенты, планирование рациона, web-дашборд, мультиарендность,
импорт внешней БД продуктов. Хочешь добавить — сперва в спеку и обоснуй.
