# CLAUDE.md — как работать в этом репозитории

burnfat — личный Telegram-бот учёта питания (2 пользователя). Главный приоритет —
**точность учёта КБЖУ**; интерфейс вторичен.

## 0. Главный принцип: спека — источник правды

- **`docs/SPEC.md` — единственный источник правды.** Любая задача начинается со сверки с ним.
- **`docs/MINIAPP-SPEC.md`** — то же для Telegram Mini App (домен, экраны, функции, инварианты
  MA-INV-*). Живой документ: решения по аппке фиксируются туда сразу, по ходу обсуждения.
- **Меняется поведение → сперва правь спеку, потом код.** Не наоборот.
- **Фиксируй в спеке всё:** требования, решения, scope, договорённости, новые открытые
  вопросы. Не держи в голове и не прячь только в коммит.
- **Отталкивайся только от спеки.** Не реализуй того, чего в ней нет, не дописав сперва туда.
  Поведение без записи в спеку = недоделка.
- Ссылайся на требования по ID: `FR-*` (функции), `NFR-*` (нефункц.), `INV-*` (инварианты),
  `AC-*` (критерии приёмки), `D-*` (принятые решения). Новый кейс/баг → заводи AC и чини до зелёного.

## 1. Архитектура (clean)

```
bot (aiogram) / web (FastAPI)  →  application (use-cases + Protocol-порты)  →  domain (чистый)
                                         ▲
                infrastructure: db (SQLAlchemy) · nlu (OpenAI/Fake) · stt (Whisper) — реализуют порты
```

- **Модель C «LLM наполняет, БД фиксирует»:** LLM извлекает сущности и оценивает плотность
  (КБЖУ/100 г); финал считает `domain/nutrition.py`; БД фиксирует плотность навсегда. SPEC §6.
- Сервисы не знают про SQLAlchemy/OpenAI. Тесты — на in-memory фейках (`tests/fakes.py`),
  без БД и без вызовов LLM.

## 2. Инварианты — НЕ ломать (SPEC §6)

- Финальные КБЖУ считает приложение, не LLM (`INV-1`).
- Плотность пиннится при первом появлении продукта → детерминизм (`INV-2`).
- `meal_items` хранят снапшот КБЖУ — история не плывёт при правке каталога (`INV-3`).
- `canonical_key` — идентичность продукта; мусорные ключи (unknown/none/food…) → slug (`INV-4`).
- Граммовка — приоритетная цепочка `resolve_grams` (`INV-7`): явный вес → штуки×вес →
  курируемый размер блюда → оценка LLM → дефолт.

## 3. Рабочий цикл

- Запуск: `make up` (db + bot + api, миграции применяются авто). Логи: `make logs`.
- **`./app` смонтирован в контейнер** → правки кода видны сразу, но процесс бота должен
  перечитать модули: **`docker compose restart bot`**. Это ЛОКАЛЬНАЯ проверка, не деплой (§4).
- ⚠️ **Локальный бот и прод — один токен Telegram.** Поднял `make up` при живом проде →
  `Conflict: terminated by other getUpdates`, два инстанса дерутся за апдейты. Для локальной
  работы либо гаси прод, либо отдельный тестовый `BOT_TOKEN`. Логика без Telegram (парсер,
  подсчёт, форматтеры) проверяется тестами и probe — бот поднимать не нужно.
- Тесты: `make test` (в контейнере). **ВАЖНО:** `./tests` НЕ смонтирован — для свежих тестов
  монтируй вручную:
  `docker compose run --rm --no-deps -v "$PWD/tests:/app/tests" api pytest -q`
- Проверить, что вернёт LLM на ввод (дегустация NLU): одноразовый probe-скрипт под `app/`,
  гонять `docker compose run --rm --no-deps api python -m app._probe`, **после — удалить**.
- Нетривиальная логика (ветка/цикл/парсер/деньги/безопасность) → оставляй один runnable-чек
  (assert-`demo()` или маленький `test_*.py`). Ponytail: без фреймворков и фикстур.

## 4. Деплой

**Прод — не этот мак.** Оба бота живут на VPS `89.124.97.90` (с 03.08.2026, ради аптайма:
мак закрыт → бот мёртв, вечерний итог не уходит). Мак — только dev.

**Деплой = пуш в `main`.** GitHub Actions (`.github/workflows/deploy.yml`) сперва гоняет **тесты**
(job `test` — гейт, красное = деплоя нет), затем идёт по ssh на сервер, делает
`git reset --hard origin/main`, поднимает compose и проверяет, что бот вышел на polling.
Ручной прогон без коммита — кнопка **Run workflow** (`workflow_dispatch`). Красный прогон =
НЕ задеплоено; причина — `gh run view --repo DaniilGreen/nutrition-bot --log-failed`.

Порядок правки: 1. спека (если меняется поведение) → 2. код → 3. тесты зелёные →
4. коммит + **пуш** → 5. дождаться зелёного прогона. README/SPEC держать в соответствии.

- Обновление ~30 сек: `./app` смонтирован, слои в кэше. Реальная пересборка — только если
  тронул `requirements.txt`/`Dockerfile`.
- На сервере `/opt/burnfat`, оверрей `docker-compose.prod.yml`: у `db` и `api`
  `ports: !reset []` — наружу не публикуем (на публичном IP это была бы открытая база с
  дефолтным паролем). Доступ к БД — `docker compose exec db psql`, к логам —
  `ssh root@89.124.97.90 'cd /opt/burnfat && docker compose logs -f bot'`.
- `.env` живёт ТОЛЬКО на сервере (chmod 600), в git его нет. Пересоздал сервер — копируй заново.
- Бэкапы обеих БД: cron `/etc/cron.d/db-backups`, 04:17, хранение 14 дней в `/opt/backups`.
- **Диск всего 10 ГБ на два проекта** — это узкое место, а не мелочь. Каждый деплой оставляет
  слои и кэш сборки; 05.09.2026 шесть деплоев подряд загнали диск в 96%. Деплой сам чистит
  висячие образы и держит кэш сборки под 512 МБ, плюс `/etc/cron.d/docker-prune` раз в неделю
  (`/opt/docker-prune.sh`) — он общий на оба проекта. `docker image prune -a` НЕ гонять: под
  него попадут образы соседа, сейчас не запущенные, но ему нужные.
- Сторож: `/opt/healthcheck.sh` раз в 10 мин (`/etc/cron.d/healthcheck`) — контейнеры живы и
  диск < 90%. Проблема → одно сообщение в телегу владельцу, при восстановлении «инцидент
  закрыт». Дедуп через флаг `/var/run/healthcheck.failing`, чтобы флап не спамил.

## 5. Коммиты (этот репо)

- Формат: `type(scope): subject` (imperative, без точки). Для крупного изменения — пустая
  строка и `#comment` на русском (что → почему → эффект, 18–30 слов). Мелкой правке — только subject.
- `type` по приоритету изменённых файлов: `infra`/`ci` > `fix`/`feat` > `refactor`/`chore` > `docs`/`test`.
- **Jira-ключа нет** — это личный проект (переопределяет глобальный формат).
- **НЕ упоминать Claude / Co-Authored-By** в сообщении.
- **Перед коммитом — гард `.env`:** `git ls-files --error-unmatch .env` должно падать
  («не отслеживается»). В `.env` реальные `BOT_TOKEN` и `OPENAI_API_KEY` — gitignored,
  НИКОГДА не коммитить и не пушить.

## 5.1 Вёрстка мини-аппа — проверять на двух крайностях

Правки вёрстки проверяются на **320 и 1100** пикселях, а не на той ширине, что
открыта. Три поломки подряд доехали до прода именно так: `max-width` на body,
`transform:scale` с процентами, растянутая сетка панели. Каждая выглядела
нормально там, где я смотрел.

`node web/check.mjs` в гейте ловит первые две формы. Третью — нет: сетка сама
по себе законна, ломает её контекст. Подробности и что мерить — `web/responsive.md`.

Там же четвёртое правило, из другого класса: **мутация не стирает экран**. `loading()`
меняет весь `#screen` на скелет — на чтении это уместно, на записи нет: высота
схлопывается с ленты до одной карточки, прокрутка прыгает, и человек видит два
скелета подряд. Занятость при записи показывает `busy()` (MA-INV-32). И пятое: **верхний отступ под вырез** —
снизу `env(safe-area-inset-bottom)` стоял в четырёх местах, сверху не стоял нигде,
и шапка уехала под часы (MA-INV-36).

## 6. Ponytail (стиль кода)

Лениво = эффективно, не небрежно. Stdlib и нативное — первым делом; не плодить абстракции
ради «на будущее»; кратчайший рабочий диск. Сознательные упрощения помечать `# ponytail:`
с указанием потолка и пути апгрейда. Не упрощать: валидацию на границах доверия, обработку
ошибок (потеря данных), безопасность, явно запрошенное.

## 7. Что сознательно НЕ делаем (SPEC §4)

Фото/штрихкоды, микронутриенты, планирование рациона, web-дашборд, мультиарендность,
импорт внешней БД продуктов. Хочешь добавить — сперва в спеку и обоснуй.
