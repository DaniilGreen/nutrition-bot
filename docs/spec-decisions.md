# Решения, отклоняющиеся от спеки

Спека (`docs/MINIAPP-SPEC.md`) по умолчанию не меняется. Сюда попадает только то,
что вскрыла реализация: противоречие, дыра или технически невозможное требование.

Форма записи обязательна целиком. **Без раздела «чем плохо» решение не принято.**

```
## D-MA-N. Заголовок — дата

**Что меняем:** …
**Почему нельзя оставить:** …
**Альтернативы:** … (перечислить рассмотренные, не только выбранную)
**Чем плохо выбранное:** … ← без этого пункта решение недействительно
**Что теряем:** …
**Правка в спеке:** §… (обязательно внесена, расхождений быть не должно)
```

---

## D-MA-1. Унаследованные нарушения ruff не чиним сейчас — 02.09.2026

**Что меняем:** ничего в спеке. Фиксируем сознательное бездействие: `ruff check app/`
даёт 29 нарушений, 28 из них в коде, написанном до мини-аппа (17 в
`app/infrastructure/products/seed.py`, остальные россыпью). Свои файлы держим чистыми.

**Почему нельзя оставить без записи:** CI гоняет только `pytest` (`.github/workflows/deploy.yml:29`),
линтера в гейте нет вовсе — поэтому нарушения копились незамеченными. Молчаливое
«ну там и так грязно» превращается в норму.

**Альтернативы:**
1. Починить всё сразу и добавить `ruff` в CI. Правит 9 файлов, не относящихся к аппке,
   и раздувает диффы этапа MA-M0 до неразличимости.
2. Добавить `ruff` в CI как есть — прогон краснеет мгновенно, деплой встаёт.
3. Добавить `ruff` с `--exit-zero` — гейт, который ничего не гейтит, худший вариант.
4. Ничего не делать и не записывать — нарушения остаются невидимыми.

**Чем плохо выбранное:** долг остаётся. Пока `ruff` не в CI, новый код может добавить
нарушений, и никто не заметит; чистота своих файлов держится только на дисциплине.
Момент «починить всё» отодвигается, а чем дальше, тем дороже.

**Что теряем:** гарантию, что стиль не поедет. Компенсируем ручным прогоном
`ruff check` на своих файлах после каждого раздела — вывод идёт в чат.

**Правка в спеке:** §8.9 — добавлена строка про линтер, отдельным пунктом в конец этапов.

## D-MA-2. Поле `signature` остаётся в data_check_string — 02.09.2026

**Что меняем:** §7.1 п.2. Было: «поле `signature` тоже исключить из HMAC-проверки».
Стало: исключается **только** `hash`, `signature` остаётся внутри `data_check_string`.

**Почему нельзя оставить:** спека была неверна фактически. Bot API 8.0 добавил в initData
поле `signature` (Ed25519), и Telegram включает его в подписываемый набор. Проверено по
`aiogram.utils.web_app.check_webapp_signature` из установленного образа — она выкидывает
только `hash`. Прогон обоих вариантов: с `signature` внутри — подпись сходится, снаружи — 401.
Спека — источник правды, и следующая сессия «починила бы код по спеке», уронив авторизацию
для всех современных клиентов. Тесты этого не поймали бы: поля `signature` в них не было.

**Альтернативы:**
1. Оставить спеку и поправить код — авторизация ляжет целиком, зелёные тесты не спасут.
2. Исключать `signature` и добавить обходной путь — усложнение ради неверной посылки.
3. Проверять Ed25519-подпись вместо HMAC — другой алгоритм, для third-party валидации;
   нам он не нужен, у нас есть токен бота.

**Чем плохо выбранное:** опираемся на реализацию aiogram, а не на первоисточник — из этой
среды `core.telegram.org` не резолвится. Если Telegram изменит правило, узнаем по отказам
в проде, а не из документации. Тест с `signature` это поймает только при смене нашей стороны.

**Что теряем:** уверенность «сверено с официальной документацией». Компенсируем тестом
`test_поле_signature_не_ломает_проверку`, который держит код и спеку от расхождения.

**Правка в спеке:** §7.1 п.2 — внесена.

## D-MA-3. Лимит $5 покрывает только вкладку AI, не разбор еды — 02.09.2026

**Что меняем:** уточняем §8.7. OQ-M3 закрыт формулировкой «gpt-5.1, жёсткий лимит $5 в месяц»,
но не сказано, что именно этот лимит ограничивает. Решено: только свободные вопросы вкладки AI
(`purpose="coach"`). Разбор еды при записи под лимит НЕ попадает.

**Почему нельзя оставить неопределённым:** реализация упирается в это на первой же строке.
Если считать общий лимит на всё, то в конце месяца перестанет работать **запись приёмов** —
основная функция, ради которой бот существует. Отказ записать съеденное из-за исчерпанного
бюджета противоречит D-28 («провал — это не записать»).

**Альтернативы:**
1. Общий лимит на всё. Отрубает основную функцию — прямое нарушение D-28.
2. Два лимита, отдельный на разбор еды. Второе число, второй счётчик, вторая причина отказа —
   а разбор стоит копейки при двух пользователях.
3. Лимит только на AI-вкладку (выбрано): дорогое и необязательное ограничено, дешёвое
   и обязательное — нет.

**Чем плохо выбранное:** расход на разбор еды не ограничен ничем. Если промпт распухнет
или кто-то начнёт слать сотни сообщений, счёт вырастет незаметно — счётчик его пишет,
но никто не остановит. Защита тут только в том, что пользователей двое.

**Что теряем:** гарантию, что месячный счёт не превысит $5 суммарно. Гарантируется только
потолок по вкладке AI. Расход на разбор еды виден в `llm_spend` с `purpose="nlu"`, когда
его туда начнут писать — сейчас пишется только `coach`.

**Правка в спеке:** §8.7 — внесена.

## D-MA-4. Слитые эндпоинты §7.2 — 03.09.2026

**Что меняем:** §7.2 перечисляет отдельные `GET /api/day/meals`, `GET /api/goal`,
`GET /api/summary` и три `GET /api/series/*`. Реализованы слитыми: `/api/day` несёт
и приёмы, и цель, и тоталы; `/api/stats/series` отдаёт ряд для всех графиков сразу.

**Почему нельзя оставить как в спеке:** каждый отдельный вызов — round-trip. На мобильной
сети четыре запроса вместо одного заметнее, чем размер ответа; экран «Итоги» рисовал бы
графики вразнобой по мере ответов.

**Альтернативы:**
1. Как в спеке, по эндпоинту на блок. Честнее по REST, но четыре запроса на один экран.
2. GraphQL или поля-селекторы. Слой абстракции ради двух пользователей.
3. Слить (выбрано).

**Чем плохо выбранное:** ответы толще необходимого. Экран «День» получает цель, даже когда
она не менялась; кэшировать по частям нельзя. Если экранов станет больше, `/api/day`
превратится в свалку — тогда придётся разделять обратно, уже с миграцией клиента.

**Что теряем:** возможность закэшировать редкоменяющуюся цель отдельно от быстроменяющихся
приёмов. При двух пользователях это не стоит ничего.

**Правка в спеке:** §7.2 — внесена.

## D-MA-5. Невозможная плотность отвергается, а не зажимается — 03.09.2026

**Что меняем:** AC-MA-29 требует клампа значений в 0…900. `PATCH /api/products/{id}`
вместо этого отвечает 400.

**Почему нельзя оставить:** зажать «310 г белка» до 100 значит молча записать не то,
что человек ввёл. Он увидит 100 и решит, что так и сохранилось — а это опечатка,
которую надо заметить, а не спрятать.

**Альтернативы:**
1. Кламп по AC. Тихая правка данных на границе доверия.
2. Кламп плюс предупреждение. Два состояния вместо одного, и всё равно надо читать текст.
3. Отказ (выбрано): на границе доверия отказ понятнее тихой правки.

**Чем плохо выбранное:** человек с опечаткой получает ошибку вместо результата и должен
исправлять сам. Кламп в домене (`clamp_density`, INV-11.2) остаётся как вторая линия —
значит правило существует в двух местах и может разъехаться.

**Что теряем:** гарантию, что правка каталога никогда не падает. Взамен получаем, что
записанное всегда равно введённому.

**Правка в спеке:** §7.2, AC-MA-29 — внесена.

## D-MA-6. Каталог общий, слияние доступно обоим и необратимо — 03.09.2026

**Что меняем:** записываем явно то, что до сих пор следовало из умолчания.
Каталог продуктов один на инсталляцию (MA-INV-7), поэтому любой из двух
пользователей может слить дубли, включая продукты, которые ел только другой.
Слияние необратимо: проигравшие строки удаляются, аудита «кто слил» нет.

**Почему нельзя оставить неявным:** это единственное действие в аппке, которое
необратимо и затрагивает данные другого человека. Умолчание здесь читается как
недосмотр, а не как решение.

**Альтернативы:**
1. Каталог на пользователя. Ломает саму модель C: плотность пиннится один раз
   на продукт (INV-2), а не на человека; два каталога — две правды про борщ.
2. Слияние только владельцем. Роль в БД есть (`users.role`), но у обоих
   пользователей она одна, и различать их — выдумывать иерархию на двоих.
3. Журнал слияний с возможностью отката. Таблица, экран, логика восстановления
   удалённых строк — заметная работа ради события, которое случается редко.
4. Оставить как есть, записав решение (выбрано).

**Чем плохо выбранное:** ошибочное слияние чинится только из бэкапа
(`scripts/restore_db.sh`, крон в `/opt/backups`), и никто не узнает, кто его
сделал. Если пользователей станет больше двух, это превратится в настоящую
проблему и потребует варианта 3.

**Что теряем:** возможность отменить слияние и понять, кто его выполнил.
Компенсируем предупреждением в интерфейсе: диалог называет число затрагиваемых
позиций истории и прямо говорит, что отменить будет нельзя.

**Правка в спеке:** §6.7 и §7.2 — внесена.

## D-MA-7. Отдельный токен для разрушающих действий — 03.09.2026

**Что меняем:** в набор токенов §6.16 добавлен `--alert:#C98A73`. `--danger:#FF453A`
теперь используется ровно там, где спека и требовала — величина перебора над целью.

**Почему нельзя оставить:** MA-INV-20 запрещает дословно — «не „ошибка ввода“, не
„удалить“». Красный стоял на кнопках «Удалить»/«Отменить», рамке ошибки, тосте сбоя и
кнопке записи голоса. Пять разных смыслов одним цветом: там, где красный несёт данные
(сколько именно съедено сверх цели), он переставал выделяться.

**Альтернативы:**
1. Разрушающие действия без цвета, нейтральным `--text-muted`. Слово «Удалить» и так
   говорит, что будет. Но необратимое действие ничем не отличается от обычного.
2. Оставить как есть и снять инвариант. Тогда перебор на графике теряет вес — а это
   главная цифра, ради которой график нарисован.
3. Отдельный приглушённый тон (выбрано).

**Чем плохо выбранное:** в наборе появился ещё один цвет, а каждый новый токен — это
плюс одно решение при каждой правке интерфейса. Терракотовый и красный на маленьком
экране можно спутать: они соседи по тону, различает их насыщенность, а не сам цвет.
Кнопка записи голоса стала синей — красная точка записи привычнее, и часть людей не
сразу поймёт, что запись идёт.

**Что теряем:** мгновенную узнаваемость кнопки записи и абсолютную однозначность
«красное = осторожно». Взамен красный снова означает одно.

**Правка в спеке:** §6.16 и MA-INV-20 — внесена.

## D-MA-8. Объём в имени старше оценки модели — 03.09.2026

**Что меняем:** в цепочку `resolve_grams` (INV-7) добавлен шаг перед всеми
прочими: если в имени позиции назван вес или объём, он и есть явный вес.
Заведён `app/domain/stated_amount.py`.

**Почему нельзя оставить:** живой случай — «Пиво Сайгон 0.3 л» записалось как
**500 г и 210 ккал** вместо 300 г и ~126. Модель поставила объём в имя, а
граммовку взяла свою оценку «кружка пива». Имя и цифра разошлись, и цифра
оказалась вдвое больше названной. Промпт при этом вообще не упоминал литры —
только «г» и «мл», хотя напитки маркируют литрами.

**Альтернативы:**
1. Только правило в промпте. Дешевле всего, но модель ошибается снова, а цена
   ошибки — вдвое завышенный приём в основной метрике проекта.
2. Спрашивать уточнение, когда имя и граммовка расходятся. Лишний вопрос на
   каждом напитке; §4.0 прямо против трения в записи.
3. Правило в промпте плюс защита в коде (выбрано).

**Чем плохо выбранное:** появилось второе место, где решается граммовка, и оно
переопределяет модель молча — в интерфейсе не видно, что цифру поправило
приложение. Разбор строки регулярками неизбежно неполон: «пол-литра» словами,
«0,33», «pint» он не поймёт. И если модель когда-нибудь начнёт писать в имя
вес сырого продукта, а в граммы — готового, защита сломает верный ответ.

**Что теряем:** возможность доверять модели в этом месте целиком. Взамен
названное человеком число больше не может быть тихо заменено предположением.

**Правка в спеке:** INV-7 в `docs/SPEC.md` — внесена.

## D-MA-9. Камера этикетки выносится в аппку — 04.09.2026

**Что решено.** `POST /api/meals/label` + кнопка камеры в поле ввода мини-аппа. Снимок
ужимается на клиенте до 1280 px / JPEG 0.82, уходит сырым телом, `Assistant.read_label`
читает КБЖУ на 100 г, карточка показывает прочитанное и спрашивает вес; ответ идёт через
общий `/api/meals/clarify` с видом черновика `label`.

**Почему.** §6.7 спеки с самого начала рисовал камеру в композере («камера = этикетка, не
фото блюда»), а раздел эндпоинтов её откладывал — спека противоречила сама себе. Первый же
день живого использования разрешил спор фактом: багрепорт #32 «Нет кнопки для фото и
расшифровки этикетки», и владелец подтвердил приоритет отдельно. Этикетка — единственный
путь к ТОЧНЫМ цифрам вместо оценки (сейчас 70 % позиций — оценки, §3.5), так что это не
удобство, а прямое попадание в главную метрику проекта.

**Чем плохо выбранное.**

1. **Второй дорогой вход без ограничителя сверху.** Vision дороже голоса и текста, а в аппке
   камера в одно касание — снять десять этикеток подряд проще, чем в чате. Лимит 6/мин
   защищает от цикла, но не от осмысленного перерасхода: месячного потолка на vision в
   проекте нет вовсе (у ассистента есть — $5, §10.1). Пока это два человека, дыра
   теоретическая; появится третий — считать нечем.
2. **Снимок не сохраняется.** В чате фото этикетки живёт у продукта (`photo_file_id`) и его
   можно перечитать глазами, когда цифры вызвали сомнение. Из аппки такого file_id нет, и
   `photo_file_id` остаётся пустым. Продукт, запиннутый через аппку, проверить будет нечем —
   придётся идти к упаковке заново. Чинится загрузкой снимка в бота отдельным вызовом, но
   это второй сетевой путь и своё хранилище.
3. **Клиент решает, что уходит на сервер.** Ужатие до 1280 px делает браузер. Мелкий шрифт
   состава на глянцевой упаковке после сжатия может стать нечитаемым, и vision вернёт
   правдоподобную чушь вместо отказа — а правдоподобная чушь с этикетки пиннится как ТОЧНАЯ
   (`source="label"`, без «≈») и портит все будущие записи продукта. Защита частичная:
   Атвотер-проверка ловит только рассогласование Б/Ж/У с калориями, а ровно списанные не с
   той колонки цифры — нет.
4. **Черновик живёт в памяти процесса.** Сфотографировал, отвлёкся на 15 минут — снимок
   протух, и переснимать надо заново (в чате состояние в FSM и живёт дольше). Перезапуск api
   теряет незавершённые этикетки молча.
5. **Разошлись пути.** Одно и то же действие теперь в двух местах с разным поведением: в
   чате вес можно дать подписью к фото и есть кнопки-пресеты из клавиатуры, в аппке — только
   карточка. Правило разбора веса поднято в домен (`app/domain/label_portion.py`), но сами
   сценарии разъезжаться будут.

**Что рассматривалось.** Оставить как есть и отвечать «фоткай в чат» — отклонено: аппка
заявлена как полноценный вход, а отсылка в чат за самой точной функцией обесценивает её.
Загружать снимок в Telegram ради `photo_file_id` — отложено: лишний сетевой путь ради
возможности перечитать снимок, которой пока никто не пользовался.

## D-MA-10. Ассистенту выданы инструменты вместо фиксированных фактов — 08.09.2026

**Что решено.** Модель ассистента получает четыре read-only инструмента (`day_totals`,
`meals_on`, `top_products`, `weight_log`) и сама решает, что запросить. Раньше был один
вызов с заранее собранной строкой фактов.

**Почему.** Строка фактов не содержала ни одного названия еды — проверено на живых данных:
763 символа, ноль продуктов. Половина осмысленных вопросов («чем добрать белок», «откуда
жир») оставалась без ответа. Владелец отклонил расширение фиксированного набора: «рацион
меняется, а каждый раз править промпт — такое себе». Довод верный на длинной дистанции:
любой заранее выбранный набор полей отвечает на заранее придуманные вопросы.

**Чем плохо выбранное.**

1. **Цена вопроса перестала быть предсказуемой.** Было ровно один вызов. Стало до четырёх,
   и каждый следующий несёт в промпте всю предыдущую переписку с результатами инструментов.
   При лимите $5 в месяц это не мелочь: вопрос с тремя раундами стоит кратно дороже прежнего.
   Потолок раундов и суммирование расхода (MA-INV-40) удерживают верхнюю границу, но средняя
   стоимость вопроса выросла и точной оценки у нас нет — узнаем по факту счётчика.
2. **Модель решает, что ей нужно, и может решить неудачно.** Она способна запросить
   `day_totals(90)` там, где хватило бы семи дней, и раздуть промпт на ровном месте. Лимиты
   аргументов режут худший случай, но не глупый выбор.
3. **Задержка ответа выросла.** Три раунда — это три обращения по сети подряд; на медленном
   мобильном интернете ассистент станет заметно задумчивее. Индикатора «думаю» на вкладке AI
   до сих пор нет (открытый пункт аудита), и теперь его отсутствие заметнее.
4. **Поверхность отказа шире.** Модель может вернуть вызов несуществующего инструмента,
   кривые аргументы или зациклиться на одном и том же запросе. Каждый случай обработан, но
   раньше их не существовало вовсе — сломаться было негде.
5. **Расход пишется одной записью на вопрос, а не на вызов.** Так проще и так работает лимит,
   но в `llm_spend` больше не видно, во сколько раундов обошёлся конкретный вопрос. Понадобится
   разбирать дорогие вопросы — придётся писать по записи на раунд.

**Что рассматривалось.** Обогатить `_facts()` продуктами, полным БЖУ, весом и долей оценок —
один вызов, предсказуемая цена, плюс ~400 токенов. Отклонено владельцем: набор полей
пришлось бы дописывать под каждый новый тип вопроса. Решение принято с открытыми глазами:
за гибкость платим ценой и предсказуемостью.

## D-MA-11. Фото блюда — гибрид «фото = состав, вес = от человека» — 16.09.2026

**Что решено.** Фото сложного блюда разбирается vision-моделью на составляющие с долями по
массе. Вес тарелки даёт человек (подпись или поле карточки), приложение делит его по долям,
спрашивает про масло и заправку и отдаёт получившийся ТЕКСТ в обычный разбор. Фото без веса
пишется оценкой «на глаз». Мини-апп и бот. Решение владельца после исследования рынка.

**На что опирались.**

- GPT-4o по одному фото — ~51% MAPE калорий, с известной массой ~29% (arXiv 2507.07048).
  Gemini 2.5 Flash: 56.6% → 39.5% (свой вес) → 20.2% (истинный вес). Масса — главная подсказка.
- NIDDK/NIH, 2026 (MyFitnessPal, LoseIt!, CalAI, Appediet на блюдах метаболической кухни): все
  занижают на ~треть, 250–345 ккал и ~30 г жира на приём, хуже всего на жирном.
- Nutrition5k (Google): нутрициолог на глаз — 41%, модель с датчиком глубины — 14–16% (но в
  лабораторной установке: камера на штативе, одна столовая).
- Рынок: SnapCalorie (LiDAR) ±80 ккал на 500 на iPhone Pro, ±130 без; Lose It Snap It — все
  компоненты в 60% фото, ±22% порция; MacroFactor — «фото → ингредиенты → база → правка»,
  ставка на прозрачность. Наш вариант — ближе всего к MacroFactor.
- Свои данные: вес называют сами в 55% и 78% приёмов; сложных блюд ~5–6%.

**Почему через текст, а не прямо в КБЖУ.** Один vision-вызов — это оценка без сэмплов согласия
(D-15) и без каталога. Запиннуть её значит навсегда положить в каталог цифру хуже текстовой
(INV-2). Текстовый путь проверен golden-набором (G5) — фото его переиспользует и добавляет только
разложение тарелки.

**Что рассматривалось.**

1. «Сфоткай и готово» (как Cal AI) — отклонено: ошибка 40–57% в приёмах, где сейчас есть вес,
   ухудшает главную метрику.
2. Датчик глубины — недоступен: WebView Telegram не отдаёт глубину (WebXR Depth Sensing есть
   только в полноценном Chrome на Android); нативное iOS-приложение ради LiDAR на части
   телефонов — новый продукт, и масло оно всё равно не видит.
3. Предмет-масштаб в кадре — отложено: дешевле, но выигрыш не измерен. Вернуться по замеру.

**Чем плохо выбранное.**

1. **Цена фото-записи — два пути вместо одного:** vision-вызов плюс обычный разбор с сэмплами.
   ~$0.01–0.03 с кэшем промпта; на 5–10 фото в неделю — меньше доллара в месяц.
2. **Задержка:** vision (~5–10 с) плюс разбор после «Записать» (~3–6 с). Две паузы вместо одной;
   компенсируем тем, что первая заканчивается редактируемой карточкой, а не записью.
3. **Разбор может переименовать составляющую** или задать уточнение варианта — это тот же UX, что
   у набранной фразы, но для фото он неожиданнее.
4. **Масло сверху, а не внутри веса тарелки** — 2–5% лишних граммов основы (MINIAPP-SPEC §6.22).
5. **Этикетка через общую камеру — два vision-вызова**: первый решает «этикетка или блюдо»,
   второй читает таблицу прежним промптом FR-27. Слить их в один дешевле (~$0.003 на снимок),
   но промпт этикетки выверен на реальных упаковках, и смешивать его с раскладкой тарелки —
   риск для самого точного входа в проекте. Вернуться, если этикеток станет много.
6. **Черновик в памяти процесса** (как у уточнений): рестарт api между снимком и «Записать»
   теряет карточку — человек переснимет.

**Замер 16.09.2026** (`tests/eval/run_photo_eval.py`, 50 блюд Nutrition5k cafe1, 150–700 г, ≥3
ингредиентов, снимок сверху; gpt-5.1; масло — чип «без»; один сэмпл разбора вместо семи в проде):

| Прогон | Режим | Медиана ошибки ккал | Средняя | Сдвиг | В пределах 20% |
|---|---|---|---|---|---|
| 1 | только фото | 28% | 38% | **+26%** | 43% |
| 1 | фото + истинный вес | 17.8% | 28% | +12% | 58% |
| 2 | только фото | **22%** | 32% | **+6%** | 41% |
| 2 | фото + истинный вес | **17.3%** | 29% | +14% | 53% |

Вес тарелки на глаз (прогон 2): медиана ошибки 29%, сдвиг −2%.

**Что показал замер и что поправлено между прогонами.**

1. **Мы завышаем, а рынок занижает.** Не за счёт масла (его в замере не добавляли), а за счёт
   плотной мелочи: бекону модель давала 59 г при истине 19–30, миндалю 115 при 58. Доли «по
   площади» усиливали это втрое — делёж веса переведён на граммовые оценки, в промпт добавлены
   ориентиры по штучному и плотному. Сдвиг «только фото» упал с +26% до +6%.
2. **Остаток +14% при истинном весе — в плотностях.** «Жареный» без видимой корочки и
   ресторанные названия тянут плотность вверх; часть расхождения — шум разметки Nutrition5k
   (у датасета известны ошибки в составе). Следующий рычаг — плотность, а не вес.
3. **С весом ошибка ниже примерно на треть** (22% → 17% по медиане), не вдвое, как у GPT-4o в
   литературе: наш путь «только фото» уже опирается на выверенный каталог, и выигрывать весу
   есть меньше. Подсказку «ошибка упадёт вдвое» в карточке это не отменяет по смыслу, но формулировку
   стоит смягчить, если прогон на своих фото это подтвердит.
4. **Имя-ключ** («baked_potato_no_oil») — 7 позиций из ~300 в прогоне 1, 0 в прогоне 2 после
   сопоставления со свободными кусками фразы.

**Сравнение с литературой** (та же метрика — ошибка ккал на блюдо): GPT-4o по фото ~51%,
Gemini 2.5 Flash 57% / с истинным весом 20%, нутрициолог на глаз 41%. Наш путь — 22% / 17%. Это
лучше опубликованных цифр, но выборка своя и мала (50 блюд, американская столовая); на русской
домашней еде цифра может отличаться — следующий замер нужен на своих взвешенных тарелках.

## D-MA-12. Недельный баланс считает только записанные дни — 17.09.2026

**Что решено.** Неделя календарная; баланс — сумма отклонений от цели по записанным дням;
«можно в день» до воскресенья с полом в базовый обмен. Макеты утверждены владельцем.

**Почему не по всем дням.** Пустой день как ноль делал бы любую неделю «в запасе» за счёт
забытых записей — ровно та дыра, которую нашла сверка с весами (§4.0). Пустой день как цель —
тоже выдумка. Честнее всего не считать его вовсе и показать «N из 7 записаны».

**Чем плохо выбранное.** Неделя с двумя записанными днями выглядит «в плане», хотя данных мало;
смягчаем подписью «N из 7». Цель берётся текущая: смена цели посреди недели пересчитывает прошлые
дни недели. Пол «можно в день» в обмен без замера — грубые 0.6 × цели.

## D-MA-13. InBody: сверка бланка, Каннингем, белок от БЖМ, расход с погрешностью — 17.09.2026

**Что решено.** Бланк InBody читается vision по отдельному промпту и проверяется внутренними
связями до сохранения. Обмен — по Каннингему (так считает сам InBody), белок — от безжировой
массы, реальный расход — из дневника и изменения жира/БЖМ по Hall 2008. Решения владельца:
цели только кнопкой; белок от БЖМ; расход показывать и предлагать; история — с 03.05.2026.

**Почему сверка, а не «доверяем модели».** На бланке ~20 чисел мелким шрифтом, и перепутать
строку легко. Но бланк избыточен: вес = жир + БЖМ, % = жир / вес, БЖМ = вода + белок +
минералы, обмен = 370 + 21.6 × БЖМ. Любая одиночная ошибка чтения ломает хотя бы одну связь.
Это дешевле и надёжнее, чем сэмплы согласия.

**Почему погрешность в центре.** InBody между днями расходится до 0.7 кг жира в строгих
условиях, в жизни — около килограмма. За месяц это ±440 ккал в оценке расхода — больше, чем
разница между сушкой и поддержанием. Предлагать цель на таком числе значит советовать шум.
Поэтому число показываем с диапазоном, а кнопку — только от погрешности 250 ккал (~два месяца).

**Белок 2.4 г/кг БЖМ на сушке, а не 2.2 из макета.** Helms 2014 рекомендует 2.3–3.1 г/кг БЖМ в
дефиците (для худых атлетов); при 20%+ жира уместна нижняя граница, 2.4 — с запасом. Пол —
1.6 г/кг веса (Morton 2018). Longland 2016 (2.4 г/кг) считал на кг ВСЕГО веса — в первой
редакции это было перепутано, поймал продуктовый аналитик. Для владельца 173 г (1.9 г/кг веса).

**Сверка «в кг веса», а не «в кг жира».** В макете было «около 5.3 кг жира» при делении на
7 700 — но 7 700 — это энергия килограмма веса смешанного состава, а не жира (9 400). Честная
формулировка — «около M кг веса, в основном жир».

**Чем плохо выбранное.**
1. Два vision-вызова на бланк (классификация + чтение) — ~$0.006; замеры редкие, это копейки.
2. Каннингем по БЖМ завязан на точность InBody; при систематическом занижении жира (у InBody
   относительно DXA — около −2.9 кг) обмен немного завышен. Оставлен выбор «по формуле».
3. Реальный расход требует двух замеров и 80% записанных дней — первые недели фича молчит.

Источники: Helms 2014 (JISSN), Longland 2016 (AJCN), Hall 2008 (Int J Obes), McLester 2020
и Frontiers in Nutrition 2024 — надёжность InBody.

**Ревью продуктового аналитика (17.09.2026), принято:** сегодня в балансе только при
превышении цели; «записанный день» > 0 ккал (для расхода — ≥ 50% цели); серая плашка «мало
записей»; история целей `goal_history`; пол «можно в день» = max(цель − 500, обмен | 1 200)
вместо 0.6 × цели (у второго пользователя вышло бы 807); проверка «чей бланк»; правила даты;
не-InBody бланки отклоняются; замер старше 180 дней не влияет на цели; «из чего ушёл вес» —
от 3 кг и 28 дней; «сходится» — до 1.5 кг; окно расхода — до 120 дней; метрика
`corrected_fields`; удаление замера; тексты без знаков; листание до 4 недель; `score` не
храним; правка полей в боте — через мини-апп.
**Не принято:** убрать переключатель источника обмена (он на утверждённом макете, стоит
копейки); убрать `activity` (профиль в БД не хранится — визард его не сохраняет, дублировать
нечего); свести три физики в один модуль (сверка по весам `reconcile.py` работает давно и
отдельно; новая сверка живёт в `energy.py`) — вернуться, если цифры на соседних карточках
начнут спорить.

**Живая проверка распознавания (17.09.2026).** Синтетический вьетнамский бланк InBody270 с
цифрами владельца (03.05.2026): классификация `body_scan`; все 17 полей прочитаны точно, нормы
в скобках и история внизу не взяты; сверка — ни одного расхождения. Регрессия: три реальных
фото этикеток по-прежнему `label`. Реальный бланк владельца — первый живой замер.

## D-MA-14. Порядок даты на бланке — по доказательствам; бланк перечитывается — 22.09.2026

**Повод.** Первый реальный бланк владельца (InBody270, вьетнамский, GA FITNESS) не принялся:
«не разобрал дату». Модель прочла её верно — `09.22.2026 15:26`, — а разбор отказал: для
любого неанглийского бланка мы жёстко брали порядок Д.М.Г и получали 22-й месяц.

**Причина архитектурная.** Порядок дня и месяца печатает прибор, а не язык бланка: вьетнамский
InBody270 печатает по-американски М.Д.Г. Привязка к языку — догадка, выданная за правило.

**Решение (MA-INV-55).** Порядок определяют числа: > 31 первым — Г.М.Д, > 12 на месте дня или
месяца — оно и решает. Обе позиции ≤ 12 — смотрим прочие даты той же распечатки (история
замеров внизу бланка, `other_dates`): одна однозначная дата задаёт порядок для всего бланка.
Ничего не решило — дата подсвечена и требует подтверждения. И главное: **нечитаемая дата
больше не отказ** — бланк с хорошими числами принимается с сегодняшней датой, подсвеченной;
человек её правит одним полем. Отказ из-за строки, которую человек и так видит на экране, —
худший из возможных.

**Чтение чисел (MA-INV-56).** Тот же бланк показал вторую беду: модель не читала, а выводила.
Жир взяла из строки PBF (22.8% как 22.8 кг), процент посчитала сама, безжировую — вычитанием;
все три числа сошлись в сверке именно потому, что были выведены из одной ошибки, и прошли
насквозь. Теперь модель сперва переписывает строки бланка (поле `rows`), и лишь потом
раскладывает их по полям; выводить запрещено, нет строки — `null`; отдельно разведены масса
жира и PBF, уровень висцерального жира и подписи шкал.

**Перечитывание.** Сверка §6.24 знает, когда чтение несвязно. Несошлось — бланк читается
второй раз, берётся чтение с меньшим числом расхождений (ponytail: одна попытка, без сведения
полей по согласию). Замер раз в месяц, лишний vision-вызов стоит около цента.

**Допуски ужаты** до ±0.2 кг и ±0.3 п.п. — это предел округления самого бланка (строки до
десятых). 0.3 кг жира — 2 800 ккал в расчёте расхода, а лишний флажок стоит одного нажатия.

**Живая проверка (22.09.2026), реальный бланк владельца.** До правок: дата — отказ; жир, %,
безжировая, минералы, обмен — неверны. После: дата `2026-09-22 15:26`, первое чтение с двумя
расхождениями, второе — связное и взято; отличия от бланка — мышцы 40.5 против 40.7, жир 20.6
против 20.9, обмен 1 899 против 1 898. Остальные поля точны.

## D-MA-15. Что ещё берём с бланка: индекс, балл, сегменты, темп и срок — 22.09.2026

**Повод.** Владелец согласовал расширение разбора бланка. Разбирали вчетвером: нутрициолог по
доказательной части, продуктовый аналитик по объёму, дизайнер по подаче, архитектор по данным.

**Берём:** мышечный индекс (SMI), балл прибора, сегментный анализ (десять чисел), темп
изменения состава и срок до цели по проценту жира, напоминание о замере.

**Не берём и почему.**
- **Соотношение талия-бёдра.** InBody 270 оценивает его по импедансу, а не лентой. В когорте
  Ravansar (9 965 человек) корреляция такой оценки с ленточным замером — r = 0.036 при значимом
  систематическом расхождении. Показывать 0.98 против порога ВОЗ 0.90 значило бы выдать шум за
  риск. Если центральная полнота понадобится — лента и талия/рост < 0.5.
- **Фазовый угол и ECW/TBW** — решение владельца; InBody 270 их и не печатает.
- **Рекомендованные прибором калории и целевой вес** — второй источник цели, спорящий с нашим
  расчётом (решение держится с D-MA-13).

**Разворот D-MA-13: балл теперь храним.** Там стояло «`score` не храним». Владелец просил
видеть разницу между замерами — храним и показываем числом с дельтой, без стрелок, цвета и
вердиктов (MA-INV-62). Балл — детерминированная функция уже показанных чисел: база 80, плюс
балл за килограмм мышц сверх нормы, минус за килограмм жира. Новой информации в нём нет, и
динамика неоднозначна: набрал по два килограмма мышц и жира — балл не шелохнулся.

**Главное архитектурное решение: новые числа проверяются отбрасыванием, а не флагом**
(MA-INV-57). Ни индекс, ни балл, ни сегменты не входят в обмен, белок, расход и цели. Цена их
ошибки — кривая картинка раз в месяц. Цена лишнего подтверждения выше: если `needs_confirm`
начнёт загораться из-за декоративного блока, человек натренируется жать «Всё верно» не глядя, и
MA-INV-50 перестанет работать там, где он нужен, — на весе и жире.

**Найденная связь.** Мышечный индекс InBody — это сумма безжировой массы четырёх конечностей,
делённая на рост в квадрате: 9.2 × 1.80² = 29.81 против фактических 29.95 на бланке владельца.
Одна связь накрывает пять самых трудных для чтения чисел — напечатанных внутри силуэта. Это же
значит, что индекс и сегменты надо брать парой или не брать вовсе: поодиночке каждое —
одиночное число без избыточности, тот самый класс, на котором обожглись в D-MA-14.

**Темп и срок.** Темп — изменение жира и безжировой между двумя последними замерами,
приведённое к месяцу, с погрешностью √2 × 1.0 кг на то же окно. Окно от 28 дней — порог общий с
расходом, второй не заводим; спортивная литература по биоимпедансу называет тот же месяц.
Срок считается по обеим массам сразу (`t = (p·W − F) / (f − p·(f + l))`): считать только жир
значит врать в оптимистичную сторону. Не рисуется, пока темп не крупнее собственной
погрешности, — прогноз на шуме это не осторожный прогноз, а выдумка (MA-INV-61).

**Цель по проценту жира** — кнопками в настройках, без значения по умолчанию: подставлять чужому
телу «норму» приложение не берётся. Единственное, на что она влияет, — срок.

**Пороги из литературы, принятые как контекст, а не как оценка.** Мышечный индекс: 7.0 кг/м² —
порог саркопении у пожилых (AWGS 2019, EWGSOP2 2019), для тридцатилетнего это пол, а не шкала.
Асимметрия сегментов: до 5% на руках и 3% на ногах — воспроизводимость прибора и естественная
разница сторон; разговор начинается с 10%. Темп потери: 0.5–1.0% массы тела в неделю (Helms
2014 на данных Garthe 2011), потеря безжировой до 20% от общей потери — норма.

**Сегменты не правятся руками** (ponytail): десять полей ввода на 320 px ради чисел, от которых
не зависит ни одна цель, не окупаются. Честное действие при расхождении — переснять бланк.

**Напоминание** — строка в боте с 35 дней, не чаще раза в 30, отметка в колонке
`users.scan_nudged_at`. Память процесса не годится: деплой перезапускает бота, а их бывает
несколько за день.

## D-MA-18. «Ещё раз» вместо «повторить сюда»; продукты по последнему разу — 13.10.2026

**Повод.** Владелец: «вчера занёс хлеб по этикетке, сегодня этикетки нет — хочу провалиться во
вчера и повторить его сегодня, не переносом». Плюс «Продукты» хочется видеть по дате и
добавлять оттуда. Варианты — макеты (артефакт «Повтор и продукты — варианты»).

**Выбрано (решение владельца):** А1+А2 — «↻ сегодня» у позиции прошлого дня и шторка с
граммовкой и днём; Б1 — сортировка «Недавние» с группами по дням; В2 — тап по продукту
открывает шторку порции, «+» пишет сразу; В1 — карточка начинается с записи, правка плотности
по кнопке. MA-INV-24 пересмотрен: тап по телу строки больше не пишет.

**Отклонено.** Б2 «История» — лента всех съеденных позиций с фильтром периода: дублирует ленту
дня, только сразу за несколько дней, и шумит повторами (протеин четыре раза — четыре строки).
В3 «Копия продукта» — пункт «съел то же ещё раз» закрыт повтором; копия нужна, только если
реально заводятся разные пачки. Появится такой случай — вернёмся.

**Почему повтор берёт снимок, а не каталог (MA-INV-67).** Человек повторяет то, что съел, а
не то, что сейчас лежит в каталоге. Иначе правка плотности задним числом меняла бы смысл
«ещё раз то же самое».

## D-MA-19. Правка на месте: запись раскрыта в ленте, одна шторка позиции, удаление с «Вернуть» — 21.10.2026

**Повод.** «Почему по плашке его сразу не отредактировать?» Карточка «Записал» дублировала строку ленты и
через 5 с уходила; тап по позиции вёл себя по-разному сегодня и в прошлые дни; удаление спрашивало
«Вы уверены?». Ресёрч: MacroFactor/Cronometer правят ИИ-ввод на месте, таймер не гасит то, что трогают
(WCAG 2.2.1), подтверждения прокликивают не читая — надёжнее «Отменить».

**Выбрано (владелец): 1Б, 2, 3.** Без карточки — новая запись раскрыта и подсвечена в ленте, тост
«Записал · Отменить». Одна шторка позиции на любой день: вес чипами, «поправить словами», «ещё раз
сегодня», «убрать». Удаление сразу, «Вернуть» 8 с.

**Отклонено.** 1А — правка внутри карточки «Записал»: два места с одним и тем же приёмом. Чипы по часу

**Почему «Вернуть» через снимок на сервере, а не отложенное удаление на клиенте.** Отложенный DELETE
теряется при закрытии аппки в эти 8 с — запись, которую человек удалил, «воскресает». Снимок на сервере
ничего не теряет молча: удалено сразу, вернуть можно 10 минут.

## D-MA-20. Масло на фото решает модель, а не вопрос; убрать позицию — до записи — 24.10.2026

**Повод.** Владелец: вопрос про масло на каждом фото — «лишние пару тапов», «сэндвич с жареной сосиской
естественно жарился на масле, спрашивать бессмысленно». И: в боте убрать картофель фри, которого не ел,
можно было только после записи, и правка выглядела как запись всего заново.

**Решение.** Модель сама оценивает масло при готовке по способу приготовления (без / 5 / 10 / 20 г) и

теряется молча: масло видно и убирается одним тапом — это дешевле двух обязательных тапов на каждом
фото, где ответ очевиден. В карточке бота у каждой позиции — «✖ убрать» до записи.

строка 10 г (≈90 ккал), видимая и убираемая. Раньше D-MA-11 спрашивал всегда, потому что масло — главный
недосчёт фото-трекеров; теперь недосчёт закрыт оценкой по умолчанию, а не вопросом.

## D-MA-21. «⚡ Частое» в боте: тот же use-case, что у чипов аппки; двойной тап — окно 5 с — 24.10.2026

**Что меняем:** у бота появляется кнопка меню «⚡ Частое» — наборы и частые продукты inline-кнопками,
тап пишет сразу в сегодня (SPEC FR-40). Паритет с чипами аппки (MINIAPP-SPEC §6.3, FR-39.5).

**Почему нельзя оставить:** в боте то, что ешь каждый день, приходилось печатать — и каждый раз это
поход в модель: деньги, секунды и шанс получить уточняющий вопрос на знакомом продукте. Аппка эту
дыру закрыла месяц назад, бот — нет.

**Принцип:** у двух каналов одна прикладная логика (clean: адаптер тонкий, use-case общий). Продукт —
тот же `log_quick`, что у чипа аппки. Набор — тот же повтор самого свежего приёма с этим именем
(`repeat`, механика FR-39.2), к которому приходит и чип аппки; разница только во входе: аппка шлёт
имя текстом в `process` и доходит до повтора через нечёткое сравнение (FR-39.4), бот берёт набор по
точному имени из `sets`. Новой формулы подсчёта нет, значит и расхождения каналов в КБЖУ быть не
может (INV-1…3).

**Альтернативы:**
- *Тап шлёт текст в обычный разбор* («творог 180 г» → `process`). Отклонено: для продукта это
  модель на каждый тап; для набора — нечёткое сравнение имени, которое на промахе (число в имени
  читается как штуки, FR-39.4) молча уходит в модель.
- *Набор по id приёма в callback.* Отклонено: id меняется с каждым повтором, а удаление исходного
  приёма сделало бы кнопку мёртвой. Имя — идентичность набора, в callback едет его короткий хэш
  (имя целиком не влезает в 64 байта: кириллица — два байта на букву).
- *Защита от двойного тапа через `IdempotencyStore` аппки.* Отклонено: там ключ генерирует клиент
  на одно намерение, у Telegram-кнопки такого ключа нет (id колбэка уникален на каждый тап — и на
  двойной тоже). Единственное, чем двойной тап отличается от второй порции, — время.
- *Подтверждение перед записью.* Отклонено тем же решением владельца, что и в аппке: записанное
  правится тут же, а лишний тап стоит дороже ошибки.

**Чем плохо выбранное:** окно 5 с — эвристика. Вторая порция в течение 5 с не запишется (ответ —
всплывашка «Уже записал…», молча не теряется). Отметки живут в памяти процесса: после рестарта бота
окно сбрасывается, на двух инстансах защиты не будет. ponytail: один процесс бота — потолок; второй
инстанс → ключ в БД.

**Что теряем:** продукты без `product_id` (не закреплены в каталоге) в боте не видны — в аппке их
чип уходит в обычный разбор. Бот берёт тот же топ-10, что и аппка, и глубже не идёт: много
незакреплённого в топе — меньше кнопок, зато в боте нет того, чего не видно в аппке. Потолки 3 набора
+ 8 продуктов: у клавиатуры нет прокрутки, как у строки чипов. Новая кнопка меню появляется у человека только после `/start` или
визарда — клавиатура пересылается не на каждый ответ.

**Правка в спеке:** SPEC FR-40, AC-96…AC-100.
